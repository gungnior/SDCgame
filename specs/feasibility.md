# 可行性评估：安卓 2D 像素搜打撤游戏（代码与美术全部由 AI 实现）

> 本文件是对项目提案的完整可行性评估，同时作为后续拆分任务的**基线依据**。
> 自包含，不需要额外背景。目标读者：项目拥有者 + 后续参与实现的编码 Agent。
> 关联文件：`specs/art-pipeline.md`（美术管线规格）。

---

## 1. 提案摘要

| 项 | 内容 |
|---|---|
| 平台 | 安卓手机（触屏） |
| 视角 | 平面俯视 2D 像素 |
| 类型 | 搜打撤（Extraction Shooter），单机 PvE |
| 系统清单 | 背包、枪械改装、人物状态、医疗、制造、藏身处建设、AI 索敌、AI 群体协同、随机地图生成 |
| 资源约束 | **代码和美术全部由 AI 实现** |
| 参照作品 | Zero Sievert（体量对标）、Nuclear Throne / Hotline Miami（朝向方案对标） |

### 结论

**技术可行（8/10）**，但项目体量约等于一个小团队 1–2 年的作品。
真正的瓶颈不是"AI 会不会写代码"，而是：

1. **集成与调优**——AI 能产出 50 个能跑的模块，让它们协同不崩是人力密集劳动。
2. **AI 群体协同**——清单里唯一一个 AI 写代码效果显著打折的系统。
3. **像素美术帧间一致性**——已通过"方向裁剪方案"大幅缓解，见 `art-pipeline.md`。
4. **持续投入的时间**——12–30 个月的项目，这是唯一真正的门槛。

**成本不是门槛**：现金总成本约 $400–1,500，token 预算 22–32 M。
**定位**（D-09）：非商用 + 免费发布 + 开源代码（GPL-3.0）——这解锁了 GPL/AGPL 开源代码与 CC-BY-NC 素材，资源池最大化。

## 2. 已冻结的范围决策

> 这些决策会渗透到代码架构和资产规范，**后期修改成本极高**。变更需在此处显式记录。

| ID | 决策 | 理由 | 状态 |
|---|---|---|---|
| **D-01** | **单机 PvE，不做真人联机** | 联机让工期 ×2.5~3.5、失败率大幅上升。紧张感用心跳音效、AI 小队压迫、死亡掉落惩罚替代 | 冻结 |
| **D-02** | **引擎：Godot 4.x + GDScript** | 2D/像素俯视主场；Android 导出成熟；GDScript 文件小、AI 生成质量高、重构可控；headless 可跑纯逻辑测试 | 冻结 |
| **D-03** | **方向裁剪：玩家 4 方向 / 普通敌人 2 方向 / Boss 4 方向** | 资产量降约 63%，风格一致性风险大幅下降。详见 `art-pipeline.md` | 冻结 |
| **D-04** | **枪械与手臂独立旋转绘制（烘焙 12 角度）** | D-03 的**成立前提**。若枪只有左右朝向，敌人朝上朝下视觉相同，游戏不可玩 | 冻结 |
| **D-05** | **全数据驱动：物品/枪械/配件/敌人/配方/掉落/房间模板全部 JSON** | AI 产出这类内容几乎不出错；后期平衡调整不需要改代码 | 冻结 |
| **D-06** | **模拟层与表现层分离，模拟层可在 PC headless 下单元测试** | 让 AI 自己跑测试验证，比来回贴报错日志省约 10 倍 token | 冻结 |
| **D-07** | **藏身处第一版为菜单式基地，不做自由摆放建造** | 自由建造是独立的 3 个月项目，性价比低 | 冻结 |
| **D-08** | **枪械改装第一版只改数值 + 锚点外观叠加，不做视觉变形** | 避免陷入"AI 画的配件对不上枪"的死循环 | 冻结 |
| **D-09** | **定位：非商用 + 免费发布 + 开源代码。项目许可证定为 GPL-3.0** | 解锁 GPL/AGPL 开源代码与 CC-BY-NC 素材。GPL-3.0 兼容 MIT/Apache-2.0/CC0/CC-BY | 冻结 → ⚠️ **2026-10-13 被拥有者推翻：改为 MIT**（GitHub 建库选择，见 `AGENTS.md` §5）。原文保留作决策记录 |
| **D-10** | **资产来源分工：通用件用现成素材，特有件用 AI 生成** | 见 §7.1。现成素材省时间最多的恰好是 AI 最弱的三块（tile 无缝、音效、UI 通用件） | 冻结 |
| **D-11** | **绝对禁止使用任何商业游戏的提取素材（含 Zero Sievert）** | 仓库公开 = 一被举报即 DMCA 下架 + 账号风险。个人自用也属侵权（见 §9.2） | 冻结 |
| **D-12** | **维护 `specs/third-party.md` 登记表，发布时随包提供署名清单** | CC-BY / CC-BY-SA / GPL 均要求署名。漏署名即侵权，且是发布后最容易被追责的点 | 冻结 |
| **D-13** | **付费/自定义授权素材一律不入公开仓库**。改为 `.gitignore` 排除 + `fetch_assets.sh` 获取脚本 + README 说明 | CraftPix、GameDev Market、pipoya 付费素材等均**明确禁止再分发源文件**；commit 进公开 GitHub 即构成再分发，直接违约。见 §9.3 | 冻结 |
| **D-14** | **国内发行定位：`不联网` + `无任何变现`（无内购、无广告、无打赏）** | 落入 TapTap 官方资质表的**案例 4**，只需「防沉迷认证 + 隐私合规」，**连软著和 ICP 备案都不需要**。见 §9.4 | 冻结 |
| **D-15** | **发行平台：TapTap 为主，好游快爆次之。放弃 Google Play** | Google Play 相关要求（AAB、Play 政策、targetSdk 合规项）全部作废 | 冻结 |
| **D-16** | **游戏内禁止任何网络请求**，不申请 `INTERNET` 权限 | 「不联网」是 D-14 成立的前提。一旦有任何网络请求，立即掉出案例 4，需要 ICP 备案 | 冻结 |
| **D-17** | **采用递进路线 `B → A → C`**，每阶段设验收门。**B 不是一次性原型，而是按 A/C 的架构只填充核心内容** | 最早验证"好不好玩"，避免投入 14 个月后才发现方向错。⚠️ **最大风险是"升级时重写"**，对策见 `roadmap-bac.md` §1 的五条硬约束 | 冻结 |
| **D-18** | **工具链：编码走 DeepSeek；美术用 ComfyUI 本地或 LiblibAI（成本 $0）** | 国内可访问、成本降一个数量级。⚠️ DeepSeek 上下文与工具调用能力与 Claude 不同，`§10.5` 的 token 对策需收紧，见 `roadmap-bac.md` §7.1 | 冻结 |

> **D-13 的含义**：**代码开源，素材可以不开源。** 仓库只放 CC0/CC-BY 素材与获取脚本，
> 付费素材由使用者自行购买后放入本地目录。这让"公开仓库"与"付费素材"得以共存，且不违约。

> **D-09 的连带影响**：项目一旦采用 GPL 代码，**整个游戏必须以 GPL-3.0 发布**（含源码）。
> 如果某天想转闭源商用，所有 GPL 代码都要重写——这是选择开源时就要接受的代价。
>
> ⚠️ **2026-10-13 更正**：许可证已改为 MIT，上述"必须按 GPL-3.0 发布"的连带影响**不再适用**
> （MIT 项目可并入 GPL-3.0 代码，该部分自身仍按 GPL 条款；GPL-2.0-only 仍禁用，见
> `third-party.md` R-06）。代价一侧反转：MIT 几乎不限制他人商用，这与"零变现"是两回事——
> 我们不收费，但不再强制衍生版开源。

| 引擎 | 评价 | 采纳 |
|---|---|---|
| **Godot 4.x（GDScript）** | 2D/像素/俯视主场；Android 导出成熟；免费；AI 生成质量好、文件小；headless 测试友好 | ✅ **首选** |

**性能热点**（若出现）再上 C# 或 GDExtension，不预先引入。

### 3.1 授权兼容性（D-09 生效后）

| 授权 | 能否用 | 条件 |
|---|---|---|
| **CC0 / Unlicense / MIT / BSD / Apache-2.0** | ✅ | 保留版权声明即可，与 GPL-3.0 兼容 |
| **CC-BY** | ✅ | 必须署名 |
| **CC-BY-SA** | ✅ | 署名 + 衍生素材同协议开源 |
| **CC-BY-NC / NC-SA** | ✅ | 署名 + 禁止商用（本项目符合） |
| **CC-BY-NC-ND** | 🚫 | **禁止修改**，游戏内无法使用 |
| **GPL-2.0** | ⚠️ | 与 GPL-3.0 **不兼容**，只能用 GPL-3.0 或更高 |
| **GPL-3.0 / AGPL-3.0 / LGPL** | ✅ | 项目整体以 GPL-3.0 发布 |
| 自定义"非商用免费" | ⚠️ | 逐条读，有的禁止再分发 |
| **商业游戏提取素材** | 🚫 | **见 D-11，绝对禁止** |

> **工程纪律**：每次引入外部代码或素材前先看 LICENSE。**混入一个 GPL-2.0 文件就可能造成授权冲突**，
> 而清理成本远高于事先检查。登记动作见 `specs/third-party.md`。

## 4. 逐系统可行性

| 系统 | 难度 | AI 写代码适配度 | 说明 |
|---|---|---|---|
| 背包系统 | 中 | ★★★★★ | 纯逻辑最适合 AI。难点在**触屏 UI 操作**，不在逻辑 |
| 医疗系统 | 低 | ★★★★★ | 部位伤害、流血/骨折/失血/疼痛，纯数值状态机 |
| 人物状态系统 | 低-中 | ★★★★★ | 与医疗合并为一个 `Vitals` 模块 |
| 枪械改装 | 中 | ★★★★☆ | 数值层易，**视觉层才是坑**（锚点叠加，见 D-08） |
| 制造系统 | 低 | ★★★★★ | 配方图 + 时间消耗，纯数据 |
| 藏身处建设 | 中 | ★★★★☆ | 第一版菜单式（D-07） |
| 随机地图生成 | **高** | ★★★★☆ | 模板拼接好写，**规则校验与"好玩"需大量人工调参** |
| AI 索敌 | 中-高 | ★★★☆☆ | 视野锥/听觉/最后已知位置，需性能优化 |
| **AI 群体协同** | **最高** | **★★☆☆☆** | 唯一高风险系统，见 §4.1 |

### 4.1 AI 群体协同架构（最高风险项）

**不要用 GOAP / 行为树起步**——AI 生成的行为树代码难调试，出 bug 时像黑盒。

```
感知层    视野锥 + 射线遮挡 + 听觉半径（脚步/枪声）→ 队伍共享感知
   ↓
小队黑板  警戒等级（放松/警觉/交战/搜索）、最后已知位置、目标分配、呼叫增援
   ↓
个体层    状态机 + 效用评分（选掩体 / 包夹 / 压制 / 撤退 / 扔雷）
   ↓
移动层    Grid + Flow Field（一次计算全场，N 个敌人共享，安卓性能友好）
```

**"看起来聪明"只需做到这 4 件事**：

1. 警戒等级在队伍内扩散
2. 环形包夹槽位分配（不同敌人占不同角度）
3. 轮流推进（一人压制、一人位移）
4. 听到枪声向声源靠拢

**性能预算**：同屏 20–30 敌人，单个 AI 决策 < 0.2 ms；路径重算错峰，每帧只算 1–2 个。

### 4.2 随机地图生成的硬规则

随机不等于好玩，必须**硬约束 + 预算**：

- 房间-走廊生成后**图论校验**：全连通；撤离点 ≥ 2；出生点与撤离点图距离 ≥ 阈值
- **最小可行走宽度 ≥ 3 格**（触屏操作，1 格宽走廊是灾难）
- **房间类型表**：普通 / 高价值 / 医疗 / 军械 / 出生 / 撤离，按类型分配**战利品与敌人预算**
- **可复现**：所有随机走 `seed`，便于复现 bug
- 死路比例、环路数量作为可调参数——**这部分靠人工反复试玩调，AI 帮不了**

### 7.1 分工依据（D-10）

| 为什么这样分 | 说明 |
|---|---|
| 现成素材真正省时的地方 | 恰好是 **AI 本来就弱的三块**：tile 无缝拼接、音效、UI 通用件 |
| 现成素材省不了的地方 | **AI 本来就强的三块**：角色、枪械、图标。且现成素材的方向数、帧序、锚点都与 D-03/D-04 规格不匹配，适配成本可能高于生成成本 |
| 核心判据 | 需要与**游戏数据一一对应**的资产（物品/配件/状态图标）必须 AI 生成，现成包给不了这个映射 |

**首发素材来源**：[Kenney **Desert Shooter Pack**](https://kenney.nl/assets/desert-shooter-pack)（**CC0**，**16×16 像素画**，标签 shooter/roguelike/pixel/ui）作为主基底，其余缺口从 [Kenney `tag:pixel` 像素包全集](https://kenney.nl/assets/tag:pixel)、[itch.io CC0 素材](https://itch.io/game-assets/assets-cc0/free/tag-asset-pack/tag-no-ai/tag-retro/tag-tileset) 与 OpenGameArt 补充。

> ⚠️ **修正记录**：早先版本的本文档曾推荐 Kenney `Top-down Shooter` 作为主基底包，**该推荐已撤销**——
> 那个包是**矢量/平滑风格，不是像素画**（不在 Kenney 的 `tag:pixel` 筛选中），
> 用作像素游戏主基底会造成风格撕裂。选素材包时必须先核实是否为像素画，判据见 `third-party.md` §4.1。
**音效**：[Freesound](https://freesound.org)（CC0 / CC-BY）+ Kenney Audio。

> **量化收益**：采用现成素材后，AI 图像生成调用次数从 4,000–5,500 降至 **3,000–4,000 次**，
> 美术侧工作量减少约 **15–25%**。但**观感提升大于数量收益**——通用件的统一度和完成度明显更好。
>
> ⚠️ **代价**：需额外开发外部素材适配脚本（量化调色板、重设锚点、裁剪方向、重排帧序），
> 这部分工作量要计入 `art-pipeline.md` §8.5，**不要当成免费午餐**。

| `CREDITS.md` | 自动生成的全部署名清单（素材 + 代码） |
| `THIRD-PARTY.md` | `specs/third-party.md` 的对外发布版 |
| 源码仓库 | 公开发布，与游戏包同版本 tag |
| 素材授权副本 | 每个外部素材的 LICENSE 原文留存于 `art/_licenses/` |

**开源对项目的正面影响**（不只是代价）：

1. **AI 工作流受益**——可以指着真实开源 Godot 游戏的源码让 AI 参照结构，生成质量明显更高
2. **免费测试者与贡献者**——尤其是数值平衡和 Bug 报告
3. **可复用仓库**——tile、UI、VFX 都可以回馈生态

### 9.2 关于提取素材（D-11）

**结论：绝对禁止，没有任何例外。**

| 场景 | 判定 |
|---|---|
| 免费发布 + 开源仓库 | 🚫 公开仓库极易被检测，一举报即 **DMCA 下架 + GitHub 账号风险** |
| 只自己玩、不发布 | 🚫 **仍属侵权**，只是无人追究 |
| 先用来做原型、发布前替换 | 🚫 高风险——美术管线会绑死在那些尺寸与锚点上，替换成本极高 |

> **正确替代**：把 Zero Sievert 当**参考规格书**（抄数值与机制，合法），素材用 Kenney 等 CC0 资源。
> 观测表模板见 `specs/reference-teardown.md`。

### 9.3 付费素材与公开仓库的冲突（D-13）

CraftPix 等付费素材条款**明确禁止再分发源文件**，而本项目是**公开开源仓库**——
commit 进 GitHub 就等于再分发，**直接违约**。

```
仓库内（公开）                     仓库外（本地）
├── code/          ← MIT（原 GPL-3.0，2026-10-13 改）   └── assets_paid/   ← 各自购买后放入
├── assets/        ← 仅 CC0 / CC-BY      （.gitignore 排除）
└── fetch_assets.sh  ← 获取脚本
```

**代码开源，素材可以不开源。**

### 9.4 🎯 国内发行合规（D-14 / D-15 / D-16）

**平台：TapTap（主力）+ 好游快爆。放弃 Google Play。**

TapTap 官方开发者文档给出了四档资质表
（[来源](https://developer.taptap.cn/docs/store/standardies-operation/)）：

| 游戏性质 | 需要提交的资质 | 上线形式 |
|---|---|---|
| 联网 + 有内购 | 版号 + 软著 + ICP 备案 + 防沉迷 + 隐私 | 「正式上线」 |
| 联网 + 无内购 | ICP 备案 + 防沉迷 + 隐私 | 「开放试玩」 |
| 不联网 + 有内购 | 版号 + 软著 + 防沉迷 + 隐私 | 「正式上线」 |
| ⭐ **不联网 + 无内购** | ⭐ **只需：防沉迷认证 + 隐私合规** | 「开放试玩」 |

> **我们的定位（D-14）正好命中最后一档——最宽松的一档。**
> **不需要版号、不需要软著、不需要 ICP 备案。**

**但这依赖两条硬约束**：

| 约束 | 为什么 |
|---|---|
| **不联网**（D-16） | 一旦有任何网络请求，就掉到「联网」两档，**立即需要 ICP 备案**（而 ICP 备案又要求版号，会形成死锁） |
| **无任何变现** | 一旦有内购就掉到「有内购」两档，**必须版号** |

#### ⚠️ 三个必须知道的风险

1. **法律上严格说仍需版号。** 《网络出版服务管理规定》第 27 条：
   「网络游戏上网出版前，必须向所在地省级出版行政主管部门提出申请」。
   **平台实践给了口子，但法律风险客观存在。** 这是保守建议与平台规则之间的差距，需自行评估。

2. **真实处罚案例**：2022 年广东肇庆公布的两起案件，被处罚的三款游戏**均无内购，纯靠广告变现**，
   **广告收益仅 114 元，被罚 5000 元**（[律师分析](https://www.mankunlaw.com/insights/shao-shi-wei-lu-shi-yi-wen-du-dong-shang-jia-yi-kuan-mian-fei-you-xi-xu-yao-qu-de-you-xi-ban-hao-ma/)）。
   → **「无内购」不等于「无变现」。加了广告就变成经营性行为，风险陡增。**

3. **连带效应：一旦变现，CC-BY-NC 素材立即违规。**
   `third-party.md` 里我们允许了 CC-BY-NC 素材，前提是**非商用**。
   → **保持完全无变现，才能继续用 NC 素材。**

> **结论：「不联网 + 无变现」这一条既是合规最优解，也是素材授权的最优解。要守住。**

#### 待确认项

| # | 事项 | 说明 |
|---|---|---|
| 1 | **「防沉迷认证」对不联网单机游戏的具体要求** | TapTap 四档都要求它。离线游戏如何满足需**提交工单确认** |
| 2 | **好游快爆（open.3839.com）的上架资质要求** | 本次只查到了其**广告联盟**的 FAQ，**开发者平台上架要求未核实** |
| 3 | **是否仍需申请软著** | 案例 4 不要求，但软著成本低、可作为保险 |

## 10. Token 估算

### 10.1 估算方法

```
① 输出 token ≈ 产出物字符数 ÷ 3.5
   （中文文档可参考 0.79 token/字符；代码约 1 token / 3.5 字符）
② 总消耗 ≈ 输出 × 系数 K
   K = 总输入/输出比。Agentic 编码中每一轮都要重发上下文，
       K 通常 8～15；返工多、上下文膨胀时达 25～30。
```

### 10.2 输出侧

| 产出物 | 规模 | 输出 token |
|---|---|---|
| GDScript 源码 | 30,000 行 × ~38 字符 = 1.14 M 字符 | ~326 K |
| 数据 JSON | 1.5 MB | ~430 K |
| 场景 / 资源（`.tscn` / `.tres`） | 1.2 MB | ~340 K |
| 测试 + 工具脚本 | 8,000 行 | ~87 K |
| spec / GDD / 架构文档 | 300 K 字符 | ~86 K |
| **输出小计** | | **~1.27 M** |

### 10.3 总消耗分档

| 场景 | K | 代码+内容 | + 美术/音频/文档 | **合计** |
|---|---|---|---|---|
| 乐观（AI 多一次成型） | 8 | ~10 M | ~4 M | **12–18 M** |
| **现实（有返工与调试）** | 15–18 | ~20–23 M | ~5 M | **25–40 M** |
| 悲观（架构反复重做） | 30+ | ~38 M | ~6 M | **60–100 M** |

> **方向裁剪方案（D-03）生效后**：美术/文档侧降至 ~2–3 M，**总预算下调为 22–32 M**。
>
> ⚠️ **注意 D-10 不会降低 token 预算**。现成素材省下的是**图像生成调用次数与美术工时**，不是 token；
> 反而因为要写外部素材适配脚本、授权审计脚本与署名生成器，**token 可能小幅增加**（约 +1 M）。
> 这两笔要分开算，不要把"省美术"误记成"省 token"。

### 10.4 换成钱与时间

| 项 | 估算 |
|---|---|
| 订阅制（Claude Max / ChatGPT Pro 等） | $240 – $3,600 / 全程 |
| API 按量（含缓存命中） | 22–32 M ≈ **$80 – $200**；悲观档 $300–500 |
| 图像生成 3,000–4,000 张（D-10 后） | **$80 – $250** |
| 外部素材采购 | **$0**（全部走 CC0 / CC-BY / CC-BY-NC 免费资源） |
| 音效素材 | **$0**（Freesound CC0 + Kenney Audio） |
| Google Play 账号 | $25 |
| **现金总成本** | **约 $400 – $1,500** |

### 10.5 ⚠️ Token 爆炸点与对策

项目超过约 20,000 行后，**单次任务上下文会涨到 80 K–150 K token**，单价相当于初期的 5–10 倍。预算超支基本都发生在这里。

1. **模块化 + 冻结接口**，每次任务只喂相关 2–3 个文件
2. **每完成一个模块就开新会话**，用 spec 文件当记忆，不要拖着一整条长对话
3. **模拟层可 headless 测试**，让 AI 自己跑测试验证
4. 每完成一个系统，**回写"架构不变量"文档**，新任务开头喂给 AI

## 14. 最终结论

1. **能落地，选单机 PvE（D-01）是正确决定。**
2. **成本不是问题**（$400–1,500，token 22–32 M），**时间和持续投入才是**。这是 12–30 个月的项目。
3. **D-09 + D-10 的定位是最省力的组合**：免费发布 + 开源解锁了最大资源池；现成素材承担通用件、AI 承担特有件是正确分工。
   但要清醒：**省下的是美术工时和图像生成次数，不是 token**，而且会新增"风格拼盘"和"规格适配"两个风险（见 §12）。
4. **最大的两个失败风险**：范围爆炸（9 个系统一起上）与 M1 阶段发现不好玩却不回头。
5. **最省钱的路径**：先花 2 周只做 M0 技术验证（安卓导出 + flow field + 随机地图链路），跑通了再写第一行游戏逻辑。这 2 周能省掉后面可能几个月的白干。
6. **架构纪律**（D-05 / D-06 / §10.5）不是洁癖，是控制 token 成本和避免 AI 改崩代码的**唯一有效手段**。
7. **D-11 没有例外**：仓库公开 + 提取素材 = 必然被举报。想省钱就往 Kenney / CC0 / Freesound 走，那里才真有免费资源。
