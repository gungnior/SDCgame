# 修订指令 4：规则检索改为「块级向量检索」，并让硬约束永远在场

> 修订 1/2/3 已完成并验收。**本文件只改检索机制，不重写任何已验收部分。**
> ⚠️ 本指令第 2.4 条**故意推翻**修订 1「不要动两轮 NEED 协议」的约束 —— 那次是保住它，
> 这次是要**替换**它。除此之外，鉴权、主题、防火墙、安全函数一行都不要动。

---

## 一、为什么要改（有实测证据，不是推测）

修订 3 完成后实测发现的**真实缺陷**：问「性感女性」，输出里出现 `soft shadows`、`warm tones`，
而技能里**明令禁止**光影/色调标签：

- `00-quick-start.md:51` 不输出光线/光影/色调标签
- `03-self-check.md:11` **灯光禁令**：无任何光线/光影/色调标签
- `13-detail-mood.md:82` 禁止列表包含 `soft lighting`、`backlighting`、`rim light` 等

**根因不是模型不听话，是检索的覆盖面问题。** 实测那次注入的三篇是：

```
00-index.md, 09-pose-solo.md, 11-camera-shot.md
```

**这三篇里一条光影规定都没有**（已逐文件核对）。禁令只存在于另外 4 个文件里。

而目录表只给模型看「文件名 + 字数 + 首行摘要」。模型看到「性感女性」，自然会点姿势、镜头；
**禁令类文件从摘要上看毫无语义引力 —— 所以每次都会漏，这是结构性的，不是运气。**

另外一个对照：Chatbox 自带的知识库用的是 **块级向量检索**（28 文件 → 120 块，top-K 跨文件取），
信息密度明显更高。本指令就是把本服务对齐到这个机制。

### 数据

| | 值 |
|---|---|
| `SKILL.md`（每轮必注入） | 3,489 字符 ≈ 2,756 token |
| `references` 28 篇全量 | 112,555 字符 ≈ 88,918 token |
| 模型上下文 | 32,768 token |
| 当前注入量 | 3 整篇 ≈ 12,000 token |

**全量注入永远不可能**（88.9K > 32.7K，即使 `-c` 提到 65536 也装不下）。
所以目标不是「全量」，而是**「硬约束永远在场 + 其余按相关性取块」**。

## 二、要实现的改动

### 2.1 建索引（切块 + 嵌入）

- **切块**：按 Markdown 结构切（标题、表格、列表块为边界），目标 **400–900 字符/块**，
  每块文本前面拼上 `【<技能名>/<文件名>】<标题路径>` 作为上下文前缀（提高检索命中率）。
- **嵌入**：`POST http://127.0.0.1:11434/api/embed`
  ```json
  { "model": "nomic-embed-text:latest", "input": ["块1文本", "块2文本"] }
  ```
  返回 768 维。**批量送，别一块一个请求。**
- **存储**：`D:\prompt-chat\index\embeddings.json`（纯 JSON，**不要引入任何依赖**）：
  ```json
  {
    "version": 1,
    "model": "nomic-embed-text:latest",
    "dim": 768,
    "builtAt": "2026-...",
    "files": { "anima3-prompt-generator/09-pose-solo.md": { "mtime": 123, "size": 5302 } },
    "chunks": [ { "skill": "...", "file": "...", "heading": "...", "text": "...", "vec": [ ... ] } ]
  }
  ```
- **规模参考**：anima3 28 篇 / 112,555 字符 → 预计 **150–250 块**；向量文件约 1–2 MB。
- **增量**：启动时比对每个源文件的 mtime+size，只重建变化的文件对应的块。
- **手动重建**：`POST /api/reindex`（带鉴权），返回块数与耗时。
- **首次启动**：索引不存在就**后台自动构建**，不要在用户请求里同步构建。

### 2.2 检索

- 用户输入 → 用同一个模型嵌入 → 与所有块算**余弦相似度** → 取 **top-K（默认 K=14，可配）**。
- **同一文件的块最多取 4 块**，避免单个大文件霸占上下文。
- 保留现有预算守卫（`budget.maxPromptTokens`）：超了就**从得分最低的块开始丢**。

### 2.3 硬约束永远注入（★ 本次修复的核心，必须做对）

在 `config.json` 增加：

```json
"retrieval": {
  "enabled": true,
  "topK": 14,
  "maxChunksPerFile": 4,
  "pinnedFiles": ["00-quick-start.md", "03-self-check.md"]
}
```

- `pinnedFiles` 里列出的文件，**其全部块无论检索得分如何都固定注入**。
- 这些块**最后才被预算守卫丢弃**（优先级高于检索块）。
- 实测这两个文件一共 4 块 / 约 5,120 字符 ≈ 4,000 token —— 预算完全够。

**这样禁令就永远在上下文里，不再依赖检索运气。这是本次唯一必须做对的事。**

### 2.4 改成单轮生成（替换两轮 NEED）

- **去掉 NEED 那一轮**：直接用 `SKILL.md` + 检索到的块（含固定块）+ 用户输入，**一次调用生成**。
- 延迟应显著下降（原来要两次模型往返）。
- `protocol.maxFilesPerRound` / `maxNeedRetries` 不再使用。
- **`skills.mjs` 里的安全函数（`safeRefFile` / `safeSkillDir` / `readRefFile`）保留** ——
  读块源文件仍然要走它们，路径安全检查一个都不能少。

### 2.5 兜底（必须保留）

- Ollama 不可达 / 索引不存在 / 索引为空 → **记警告，回退到现有的整篇文件选择逻辑**。
- 服务在 Ollama 挂掉时必须仍然可用（降级，不是罢工）。

### 2.6 输出与 UI

- `openai-compat.mjs` 里那行 `> 已加载规则：` 改成列出**来源文件（去重）+ 块数**，并把固定注入的标出来：
  ```
  > 已加载规则：14 块 / 6 个文件（固定：00-quick-start.md, 03-self-check.md）
  > 检索：09-pose-solo.md, 11-camera-shot.md, 13-detail-mood.md, 04-slot-order.md
  ```
- 网页版状态行的「规则 N 篇」改成「规则 N 块」。

### ⚠️ 一个环境陷阱（我踩过，你必须知道）

**从命令行启动 Electron 应用（比如 Chatbox）之前，必须先清掉环境变量 `ELECTRON_RUN_AS_NODE`。**
本机这个变量存在（DSH 自己也是 Electron）。不清的话 Chatbox 会被当成纯 Node 执行，
**立刻退出、无窗口、无日志、退出码 0**，看起来像"启动坏了"。

```powershell
Remove-Item Env:\ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
```

## 四、验收清单（逐条跑，把结果贴回来）
