# 是否迁移到 WorkBuddy / 多人协作的评估

> 结论先行：**不建议整体迁移；建议"核心留 DSH + 冷轨道分给 WorkBuddy"的混合模式。
> 而最高价值的用法不是并行写代码，是【对抗性验收】—— 你已经有成功先例。**
>
> 本文所有判断都基于**本项目自己的数据**（git 历史、746 项测试、真机遥测记录），不是泛泛而论。

---

## 一、先弄清 WorkBuddy 是什么

[腾讯 WorkBuddy 开放平台](https://tech.cnr.cn/techph/20260902/t20260902_527802481.shtml)于 2026-09 上线，
定位是"同时打通软硬件、开发者三层生态的 Agent 基座"。
有"小队模式"：**探索 / 执行 / 评审 / 专家顾问** 四个角色。

腾讯自己在[《WorkBuddy 实战蓝皮书·多 Agent 篇》](https://cloud.tencent.com.cn/developer/article/2751934)里的总结：

> **多 Agent 的价值不在角色数量，而在分工、交接、验收与降级这四张设计图。**

**这句话就是本文的评估框架** —— 下面逐张图对着本项目的真实数据看。

## 二、⚠️ 先说一个已经存在的"交接"事故

本仓库 `specs/` 下有 **8 份 `prompt-chat-*.md`**，它们描述的是**另一个项目**
（`D:\prompt-chat` 本地模型提示词服务），而且是**写给 WorkBuddy 的任务指令**。

它们是在**初始提交 `e06353d`** 就一起进来的：

```
e06353d init: 项目规划文档（8 份 spec）+ 数据/自动化工具骨架
```

也就是说：**同一个 `specs/` 文件夹被两个不同项目共用过**，
而"搜打撤"这个项目从一个**混入了别的项目文档**的状态开始。

更值得注意的，是那些文档里反复出现的这句话：

> 「修订 4 的检索实现是**规格作者本人（我）写的，不是 WorkBuddy 写的**」
> 「修订 3 的兼容层（**WorkBuddy 自己写的**，也要重验）」

**这正是一次"交接"出问题的记录** —— 复验者分不清某个文件是谁写的，
于是不得不让下一轮"重验所有东西"。**这正是多 Agent 的第一号风险。**

**建议先修**：把这个项目自己的 spec 与 prompt-chat 的分开
（`specs/` 保留本项目，另一个项目的移到它自己的仓库或 `specs/archive/`）。

## 三、四张设计图，对着本项目的数据看

### 3.1 分工：**可并行的轨道很清晰，但两个文件卡在所有轨道交汇处**

⚠️ **先纠正我自己一个不准确的初稿说法**：我一开始写"约一半工作量堵在 2 个文件上"。
按**文件改动行次**算是错的 —— 4 个热点文件只占 470 行次里的 **13.8%**。
但那个指标本身就不对：**工作量不等于冲突风险**。

**正确的指标是「多少【提交】必须碰这些文件」**（36 次提交）：

| 指标 | 值 |
|---|---|
| 碰 `test/run_tests.gd` 的提交 | **24 / 36 = 67%** |
| 碰 `view/raid_scene.gd` 的提交 | **18 / 36 = 50%** |
| **碰其中任一的提交** | ⭐ **26 / 36 = 72%** |
| 碰 `data/` 的提交 | 8 / 36 = 22% |
| 碰 `art/` 的提交 | 5 / 36 = 14% |

> **72% 的功能提交必须动这两个文件之一。**
> 这不是"它们占了一半工作量"，而是
> **"几乎所有功能都会在它们身上汇合"** —— 这对**并发写**是更糟的消息，不是更好的。

按模块的行次分布（供参考）：

```
art/    141 次   ✅ 生成产物，可并行
sim/     89 次   ✅ 但分散在 58 个文件 -> 模块内可并行
test/    60 次   ❌ 集中在 run_tests.gd 一个文件
view/    32 次   ❌ 集中在 raid_scene.gd 一个文件
data/    18 次   ✅ 纯数据
```

**根因是两个上帝对象**：

| 文件 | 拆分前 | **拆分后** | 状态 |
|---|---|---|---|
| `test/run_tests.gd` | **3439 行 / 59 套件** | **110 行**（只做发现+调度+守卫）<br>+ 10 个套件文件（最大 480 行） | ✅ **已拆** |
| `view/raid_scene.gd` | **1676 行 / 51 函数** | **1403 行**<br>+ `raid_hud.gd` 203 行<br>+ `raid_map_baker.gd` 196 行 | 🟡 **部分拆** |

**实测：拆分后测试数从 746 涨到 793** ——
因为拆的时候发现 **4 个 `_test_*` 函数定义了却从未注册**（89 行，静默不执行），
补注册后又发现**其中一个一直是坏的**（升级会涨价，钱给少了）。
详见 `test/test_kit.gd` 里的结构性守卫说明。

**剩下的 `_draw`（181 行 / ~40 个成员引用）尚未拆** ——
它是纯追加型、确实该拆，但抽取面比前两块大得多（要跨坐标空间与 z 序），
值得单独一轮做并用像素级 diff 验证。

**可并行的轨道（建议分给 WorkBuddy）**
- `data/*.json` 内容填充（C 阶段的 40 配方 / 更多枪械敌人）
- `tools/` 与 `art/`（Python 管线，与游戏代码零耦合）
- **`test/suites/*.gd` 新增套件** —— 拆分后每个文件独立，两人各加一个套件不再冲突
- **`view/raid_hud.gd` / `raid_map_baker.gd`** —— 拆分后各自独立可改
- 独立的新 UI 面板（`ui/*.gd`，彼此不引用）

**不可并行的（必须单一作者）**
- `view/raid_scene.gd`（虽然已瘦身，`_draw` 与模拟调度仍在里面）
- 手感调参（hitstop/trauma/后坐力）—— 这是**审美判断**，多人调只会互相打架

### 3.2 交接：**本项目已经踩过很多次，而且都是同一类**

本会话修复的缺陷里，有一类**恰恰是多 Agent 会放大**的：

| 缺陷 | 次数 | 性质 |
|---|---|---|
| `Control` 尺寸塌成 0 | **3 次**（摇杆/结算/设置菜单） | **跨模块不变式** |
| `get_tree().paused` 打补丁而非换掉 | **2 轮** | 机制理解 |
| 度量不一致（遥测修了 HUD 漏改） | **2 次** | 跨切面 |
| 新增字段忘了在转换函数里带上 | **3 次**（treat / _load_attachments / aim_cone_deg） | **跨文件契约** |
| 补丁 marker 用了别处也存在的字符串 → 静默跳过 | 1 次 | 工具严谨性 |

**共同点：这些都不是"某个模块内部的 bug"，而是"两个地方必须保持一致"。**
它们**已经**在单 agent 下反复出现了。

> ⚠️ **多 Agent 会把这类问题变多，不会变少** ——
> 因为每个 agent 只知道自己那一块。这是我最担心的一点。

**降风险的具体做法**（无论用不用 WorkBuddy，都值得做）：
1. **把测试拆成多文件** —— `test/run_tests.gd` 2938 行是最大冲突源
2. **写入范围（write scope）显式化** —— 每个任务声明"我只会改哪些文件"
3. **禁止两人同时改同一个文件** —— 尤其 `raid_scene.gd`
4. **契约测试先行** —— 像"`aim_cone_deg` 必须在 `to_weapon_def()` 里被复制"这种断言，
   就是防交接遗漏的。这类断言**已经存在**，是资产。

### 3.3 验收：**这是本项目最强的一块，而且是模型无关的**

本项目已经有一整套**可移植的验收基础设施**：

| 资产 | 规模 | 迁移成本 |
|---|---|---|
| `test/run_tests.gd` | **746 项断言** | 零（就是 GDScript） |
| `test/pc_verify.tscn` | 51 项端到端集成检查 | 零 |
| 布局探针（menu/hideout/merchant/result） | 5 个 | 零 |
| `tools/validate_data.py` | 数据契约校验器 | 零 |
| `tools/monitor_game.py` + `telemetry/` | 真机遥测直连 | 需 adb，WorkBuddy 侧要能跑 |

**这意味着：换任何 agent 来做，验收标准都不变。**
这是本项目相对"靠人肉 review"的项目最大的优势，也是**迁移风险最低的部分**。

> 反过来说：**如果 WorkBuddy 不能跑 `godot --headless --script res://test/run_tests.gd`，
> 那它就不该接这个项目的执行工作** —— 因为那等于把唯一的护栏拆了。

### 3.4 降级：**本项目已有成熟路径**

- 遥测挂了 → 还有截图
- 截图不行 → 还有探针（打印控件位置/尺寸）
- 探针不行 → 还有 746 项单测
- 全部不行 → 还有 git（29 次提交，粒度小，可回滚）

**这条链是完整的，迁移后要保证 WorkBuddy 侧也能走完它。**

## 四、⭐ 最高价值的用法：不是并行写代码，是**对抗性验收**

这是我认为最该复制的一件事。

你之前对 WorkBuddy 的用法里，有一段写得非常专业（`prompt-chat-revision-4-verify.md`）：

> ⚠️ **这次的实现者是规格作者本人（我），不是 WorkBuddy。**
> 所以你的任务**不是"确认它能用"，而是尝试证明它不能用。**
> 报告里我给出的每一个数字，你都要用**自己的命令**重新跑一遍。**不要采信我的数字。**

而且你给了**具体的诱导用例**（8 条需求 × 3 次 = 24 次），而不是"随便测测"。
**这套模式对本项目同样适用，而且价值极高**，因为：

- 我自己发现的 bug 里，**至少有一半是"我以为对了"的**
  （对称性假设、包夹点稳定性、`at_index` 语义、双重随机判定…）
- 我是**实现者**，天然有确认偏误
- 你已经有证据表明 WorkBuddy 能做这种"证明它不能用"的活

**具体建议：下一轮把"评审"角色分给 WorkBuddy，任务是**：

> 以下是我（实现者）声称已完成的 N 项。**你的任务不是确认，是证伪。**
> 每一条都要用**你自己的命令**重跑，不许引用我的数字。
> 找不出问题就写"未能证伪"，**不许写"通过"**。

**候选证伪清单（本项目现存弱点）**：
1. 存档在**安卓**上是否真的走 `user://`（PC 上走的是可移植回退，**两条不同代码路径**）
2. `MAX_TEST_ENEMIES=4` 关掉后，35 敌人的满编局性能如何（**从没测过**）
3. 包夹 AI 在**狭窄走廊**里是否会互相卡住（测试只覆盖了开阔地）
4. 存档迁移链在**跨 2 个版本**（v1 直接升 v3）时是否正确
5. 掉落表过滤后，**B 档的总掉落量**是否比过滤前少（我按推理说"不会少"，**没有实测**）

## 五、迁移成本与收益（诚实估算）

| 项 | 评估 |
|---|---|
| **代码迁移成本** | **≈ 0** —— Godot + GDScript + Python + git，没有任何 DSH 专有依赖 |
| **验收基础设施** | **≈ 0** —— 746 测试 / 探针 / 校验器全是标准脚本 |
| **工作流迁移成本** | **中** —— 遥测走 adb、探针模式、"先看数据再改代码"的习惯需要重建 |
| **上下文迁移成本** | **高** —— 本会话积累的**踩坑记忆**（Control 尺寸 3 次、paused 2 轮、字段漏拷 3 次）不在代码里，在对话里。换环境等于**从零再踩一遍** |
| **并行收益** | **中** —— 只有约一半工作量可并行（见 3.1） |
| **并行风险** | **中高** —— 跨模块不变式类 bug 会被放大（见 3.2） |

**关键判断**：
> **代码迁得走，踩坑记忆迁不走。**
> 而这个项目到目前为止，**大部分时间花在"踩坑并固化"上，不是花在"写新代码"上**。

## 六、建议

### 不建议做
- ❌ **整体迁移到 WorkBuddy** —— 可并行的只有**冷轨道**（`data/` / `tools/` / `art/` / 独立 UI），
  而 **72% 的功能提交都要碰 `run_tests.gd` 或 `raid_scene.gd`**。
  收益抵不上成本（踩坑记忆重建 + 跨模块不变式风险）
- ❌ **让多个 agent 同时改 `raid_scene.gd`**
- ❌ **让多个 agent 一起调手感参数**

### 建议做（按优先级）
1. **立刻修 `specs/` 污染** —— 7 份 prompt-chat 文档移出本项目
2. ~~拆 `test/run_tests.gd`~~ ✅ **已完成**（3439 → 110 行 + 10 个套件文件）
3. ~~拆 `view/raid_scene.gd` 的 HUD 与地图烘焙~~ ✅ **已完成**
   （1676 → 1403 行，另抽出 `raid_hud.gd` / `raid_map_baker.gd`）
4. **继续拆 `view/raid_scene.gd` 的 `_draw`**（181 行 / ~40 个引用）
5. **给 WorkBuddy 分"冷轨道"**：`data/` 内容填充、`tools/`+`art/` 管线、
   **`test/suites/` 新增套件**、独立新 UI 面板
6. **给 WorkBuddy 分"评审角色"**（最高价值）：用上面 §4 的证伪清单，
   模式照抄你 `prompt-chat-revision-4-verify.md` 的写法
7. **核心执行（`view/raid_scene.gd`、`sim/ai/`、手感调参）留在单一 agent**

### 一张图总结

```
                可并行                          不可并行
        ┌──────────────────────┬──────────────────────────┐
        │ data/*.json          │ view/raid_scene.gd       │
        │ tools/ + art/        │ test/run_tests.gd        │
        │ 独立 ui/*.gd 面板     │ 手感调参（审美判断）      │
        │ 独立 sim/ 模块        │ 版本号/配置              │
        └──────────────────────┴──────────────────────────┘
              ↑ 给 WorkBuddy        ↑ 保持单一作者
              
        ⭐ 最高价值：WorkBuddy 做【评审】而不是【执行】
```

## 七、一句话回答你的问题

> **可以协作，但"转移项目"不是关键，"分工/交接/验收/降级"这四张图才是。**
> 本项目的**验收**这张图已经画好了（746 测试 + 探针 + 校验器，且与 agent 无关）——
> 这是它最值钱、也最该被复用的部分。
> 而**交接**这张图**已经出过事故**（`specs/` 里混着另一个项目、以及"分不清谁写的"）。
> **先把交接修好，再谈加人。** 否则加进来的人只会更快地把坑踩一遍。
